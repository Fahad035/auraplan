# ADR 0005: API Boundary Validation

- **Status:** Accepted
- **Date:** 2026-10-21

## Context

The browser, serverless API, and generative AI provider exchange data across runtime boundaries. TypeScript types alone do not validate JSON received over HTTP or content generated by a model. Unexpected or malformed data can lead to application errors or invalid recommendations.

## Decision

Use Zod to validate incoming API request fields at runtime. Validate the structure and bounds of generated data before returning it to the frontend, and keep the frontend API client defensive about unsuccessful responses and unexpected payloads.

Schemas should be explicit about accepted fields, types, sizes, and ranges. Validation errors returned to users should not expose secrets or internal implementation details.

## Alternatives considered

- **TypeScript types alone:** rejected for untrusted runtime input because types are erased at runtime.
- **Manual validation only:** possible, but can become repetitive and inconsistent.
- **Runtime schema validation with Zod:** selected for readable schemas and integration with TypeScript.

## Consequences

### Positive

- Invalid input can be rejected before it reaches downstream processing.
- Validation rules are easier to centralize and test.
- API consumers receive a more predictable response contract.

### Trade-offs

- Schemas must evolve alongside frontend and backend features.
- Valid structure does not guarantee that AI-generated recommendations are factually correct.
- Output validation must be combined with limits, safe error handling, and appropriate HTML rendering practices.

## Revisit when

Reconsider the schema approach if the API becomes substantially more complex or needs shared schemas across multiple services. Any schema change should include tests for valid input, invalid input, boundary values, and malformed model output.
